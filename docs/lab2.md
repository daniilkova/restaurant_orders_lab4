# Restaurant Orders API — лабораторная работа №2 (вариант 9: Ресторан и заказы)

Продолжение лабораторной №1: тот же API заказов, но уже с настоящей БД, Redis, Celery и админ-панелью.

## Пять улучшений варианта 9

| № | Требование | Где реализовано |
|---|-----------|-----------------|
| 1 | Постоянное хранилище: `orders`, `dishes`, `order_items` | `app/models/`, миграция `alembic/versions/0001_initial.py`. Заказ содержит несколько блюд; цена и название блюда копируются в `order_items` в момент заказа |
| 2 | Кэш меню: `GET /dishes` на 1 минуту | `app/routers/dishes.py`, `app/redis_client.py` (`get_cached`). Кэш сбрасывается при POST/PUT/DELETE блюда и при правках в админке |
| 3 | Rate limit: 20 заказов в минуту с одного IP | `rate_limit()` в `app/redis_client.py` (Redis `INCR` + `EXPIRE`), подключён к `POST /orders`. При превышении — `429` и заголовок `Retry-After` |
| 4 | Фоновая задача: через задержку «доставляется», затем «завершён» | `app/tasks.py` (Celery), задержки задаются `COOKING_DELAY_SECONDS` и `DELIVERY_DELAY_SECONDS` |
| 5 | Админ-панель: текущие заказы в реальном времени + ручная смена статуса | `/dashboard/` — живая таблица (обновляется раз в 3 секунды, статус меняется выпадающим списком); `/admin` — полноценная админка (sqladmin) для блюд, заказов и позиций |

## Запуск через Docker (рекомендуется)

```bash
docker compose up --build
```

Поднимутся PostgreSQL, Redis, API (миграции применяются автоматически), Celery-воркер и Flower.

| Что | Адрес | Доступ |
|-----|-------|--------|
| Swagger | http://localhost:8000/docs | — |
| Админка | http://localhost:8000/admin | admin / admin |
| Заказы в реальном времени | http://localhost:8000/dashboard/ | admin / admin |
| Flower (мониторинг Celery) | http://localhost:5555 | admin / secret |

Масштабирование воркеров: `docker compose up --scale worker=3`.

**Как проверить фоновую задачу:** в Swagger создайте блюдо (`POST /dishes`), затем заказ (`POST /orders`) и откройте `/dashboard/`.
Через 20 секунд статус станет «доставляется», ещё через 20 — «завершён» (заказ исчезнет из списка активных). В логах `worker` видны строки `Заказ 1 -> доставляется`.

## Запуск без Docker

```bash
python -m venv venv
venv\Scripts\activate            # Windows (Linux/macOS: source venv/bin/activate)
pip install -r requirements.txt
alembic upgrade head             # создаст SQLite-файл app.db
uvicorn app.main:app --reload
```

- Без Redis API работает (кэш и rate limit временно отключаются), но фоновые задачи без Redis не запустятся.
  Быстро поднять Redis: `docker run -p 6379:6379 redis:7-alpine`.
- Воркер: `celery -A app.celery_app worker --loglevel=info` (на Windows добавьте `-P solo`).
- Настройки — через переменные окружения, см. `.env.example`.

## Эндпоинты

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/dishes/` | меню (кэш 1 мин) |
| GET/PUT/DELETE | `/dishes/{id}` | блюдо; удалить блюдо, уже попавшее в заказы, нельзя (409) |
| POST | `/dishes/` | добавить блюдо |
| GET | `/orders/` | заказы (`?status=`, `?skip=`, `?limit=`) |
| GET | `/orders/{id}` | заказ с позициями и суммой |
| POST | `/orders/` | создать заказ `{"items": [{"dish_id": 1, "quantity": 2}]}` (лимит 20/мин с IP) |
| PUT | `/orders/{id}` | заменить состав и статус |
| PATCH | `/orders/{id}/status` | сменить статус `{"status": "готовится"}` |
| DELETE | `/orders/{id}` | удалить заказ |

## Ответы на вопросы для закрепления

1. **Зачем async-драйвер SQLAlchemy?** Пока запрос ждёт ответа БД, event loop может обслуживать другие запросы. Синхронный вызов внутри `async def` блокирует весь процесс, и под нагрузкой API «встаёт». Async-драйвер плюс пул соединений позволяет одному процессу обрабатывать много конкурентных запросов.
2. **Кэш с TTL и инвалидация.** Значение хранится в Redis N секунд и потом удаляется автоматически. Инвалидация — принудительное удаление или обновление кэша, когда данные изменились (в проекте — удаление ключа `dishes:list` при изменении меню). Стратегии: только TTL; cache-aside с явной инвалидацией (наш вариант); write-through (пишем в БД и кэш одновременно); write-behind; версионирование ключей.
3. **`delay` и `apply_async`.** `task.delay(*args, **kwargs)` — короткая запись `apply_async(args, kwargs)` без параметров запуска. `apply_async` принимает опции: `countdown`, `eta`, `queue`, `expires`, `priority`, `retry`. Мы используем `apply_async(countdown=...)`, чтобы отложить задачу.
4. **Разные лимиты для разных эндпоинтов.** Лимитер — фабрика зависимости `rate_limit(max, window)`. Для каждого маршрута указывается своя пара чисел в `dependencies=[...]`, а ключ в Redis включает метод, путь и IP, поэтому счётчики независимы. Для глобальных лимитов подойдёт middleware со словарём «маршрут → лимит».
5. **Масштабирование Celery.** Запустить больше воркеров (`--scale worker=N`, несколько машин), увеличить `--concurrency`, развести задачи по очередям (быстрые и тяжёлые отдельно), использовать autoscale, следить за очередями во Flower. При очень большой нагрузке — перейти на RabbitMQ или Redis Cluster как брокер.
6. **Что не стоит кэшировать.** Персональные и приватные данные (профиль, корзина, токены), если ключ не привязан к пользователю; быстро меняющиеся критичные данные (остатки, баланс, статусы платежей); ответы на изменяющие запросы (POST/PUT/DELETE); ответы с ошибками; секреты и пароли.

## Заметки по реализации

- Фоновая задача ставится в очередь **после** `commit()`, иначе воркер мог бы не найти заказ в БД.
- `apply_async` синхронный (работа с сетью), поэтому вызывается через `run_in_threadpool`, чтобы не блокировать event loop.
- Если брокер недоступен, заказ всё равно создаётся, ошибка пишется в лог.
- Redis недоступен — кэш пропускается, rate limit отключается (fail-open); это осознанный выбор доступности вместо строгости.
- Счётчик лимита: `INCR` + `EXPIRE` при первом запросе окна. Если процесс упадёт между двумя командами, ключ останется без TTL — для production используют Lua-скрипт или `SET NX EX`.
- За обратным прокси (nginx) IP клиента берётся из заголовка `X-Forwarded-For`, для этого запускайте uvicorn с `--proxy-headers`.
- Пароль админки и `SECRET_KEY` в `docker-compose.yml` — учебные, в production их нужно менять.
